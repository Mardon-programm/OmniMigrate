# OmniMigrate — Roadmap to 10/10

Цель: довести продукт до **10/10 во всех измеряемых параметрах**. Ниже —
определение «10/10» по каждой сфере, фазы работ с оценкой трудозатрат,
приёмочные критерии и приоритеты.

---

## Определение «10/10» (что означает идеальная оценка)

| Сфера | 10/10 означает |
|---|---|
| **Архитектура** | Все слои изолированы, события/асинхронность последовательны, нет демо-заглушек, каждая подсистема имеет единый владелец-модуль |
| **Тесты** | CI обязательно гейтит merge; coverage ≥ 85%; unit + integration + e2e; каждая новая фича требует тест до мерджа |
| **Безопасность** | SSO (SAML/OIDC) + MFA, RBAC на уровне организации, audit log, секреты не в БД/Redis, изолированный sandbox, zero-trust для токенов |
| **Масштабируемость** | Горизонтальное масштабирование воркеров, очереди с приоритетами, лимиты на tenant, нагрузочный тест (k6) с целевым RPS |
| **Бизнес** | Планы/биллинг (Stripe), метрики использования, инвойсы, лимиты по планам, самообслуживание |
| **Готовность к enterprise** | SOC 2 readiness, SLA, audit, SCIM-провижининг, on-prem опция, контрактная документация |
| **UX/UI** | Dark-first emerald-дизайн, полный флоу git-пайплайна в UI, онбординг, доступность (a11y), i18n |
| **Документация** | Docs-сайт, архитектурные диаграммы, API-референс, runbook, troubleshooting |

---

## Фаза 0 — Фундамент качества (нед. 1) · ~5 дней

Фундамент, без которого не бывает «10». Делается первым и включает всё.

- [x] CI/CD (GitHub Actions): ruff, pyright/mypy, pytest+coverage, vitest, docker build — гейт на каждый PR.
- [x] pre-commit hooks (ruff format, check).
- [x] ruff + pyright конфиги в репо (сейчас их нет).
- [ ] Интеграционные тесты API против реального Postgres (testcontainers).
- [x] Политика: «feature = тесты + документация» — чек-лист в PR-шаблоне.
- [x] Coverage gate 85% на backend и frontend.

**Приёмка:** пустой репозиторий → один `git push` → все проверки проходят зелёными.

---

## Фаза 1 — Enterprise-безопасность (нед. 2–4) · ~20 дней

- [ ] SSO: SAML + OIDC (Auth0 / Keycloak / custom), MFA, session management.
- [ ] Организации/тенанты: модель Organization → Team → User; роли owner/admin/member/viewer.
- [ ] RBAC на уровне ресурсов (projects/jobs внутри организации).
- [ ] **Audit log**: сервис записи «кто/что/когда/с каких данных» + API + UI.
- [ ] Секреты: GitHub-токены шифруются (KMS/Vault) и **никогда** не попадают в Redis/аргументы arq.
- [ ] Изоляция sandbox: job в отдельном контейнере (ephemeral Docker / DinD) с ulimits, cgroups, без сетевого egress кроме allowlist.
- [ ] SSRF-хардненинг: DNS-rebinding защита, валидация IP перед клоном.
- [ ] Rate limit на организацию (не только глобально).

**Приёмка:** аудит-лог фиксирует каждый чувствительный вызов; токен недоступен даже из Redis-дампа.

---

## Фаза 2 — Глубина продукта (нед. 4–7) · ~25 дней

- [ ] **UI git-пайплайна**: форма repo/token/branch, живой прогресс, просмотр PR-дифа до пуша.
- [ ] PR-интеграция: draft-PR, labels, reviewers, комментарии к строкам дифа.
- [ ] Мультиязычность: JS/TS, Java, Go; фреймворки (Django→FastAPI, jQuery→React).
- [ ] Review-флоу: approve/reject миграции, apply к репозиторию, откат.
- [ ] Job management: cancel/retry/pause, webhook-уведомления (внешние).
- [ ] **Метрики использования**: jobs, LLM-токены, файлы, минуты — по организации.
- [ ] Эвристики качества миграции (score, риск-анализ изменений).

**Приёмка:** пользователь проходит флоу «вставил repo → получил PR → approve» без выхода из UI.

---

## Фаза 3 — Бизнес-слой (нед. 7–9) · ~20 дней

- [ ] Биллинг: Stripe (Free / Team / Enterprise), metered billing по метрикам.
- [ ] Инвойсы, receipt, billing portal, self-serve upgrade/downgrade.
- [ ] Лимиты и квоты по планам (jobs/мес, файлы, LLM-токены).
- [ ] Организационный онбординг: приглашения, инвайт-ссылки.
- [ ] SCIM-провижининг пользователей из корпоративного IdP.
- [ ] Дашборд usage для клиента и админа.

**Приёмка:** клиент регистрируется, платит картой, видит счёт и лимиты — без звонка менеджеру.

---

## Фаза 4 — Масштаб и надёжность (нед. 9–11) · ~20 дней

- [ ] Горизонтальное масштабирование воркеров; приоритетные очереди (urgent/normal/bulk).
- [ ] Observability: OpenTelemetry, Sentry, Prometheus/Grafana, структурированные логи.
- [ ] Резервное копирование и восстановление Postgres/Redis; DR-плейбук.
- [ ] Нагрузочное тестирование (k6): целевые RPS и latency-p99.
- [ ] Graceful degradation: LLM-падение → правила → очередь → уведомление.
- [ ] Multi-region опция (для enterprise).

**Приёмка:** k6 держит целевой RPS с p99 < 1s; отказ Redis не роняет API.

---

## Фаза 5 — GTM и документация (нед. 11–12) · ~15 дней

- [ ] Marketing-сайт: позиционирование, use-cases, pricing page.
- [ ] Docs-сайт: архитектурные диаграммы (Mermaid/C4), API-референс, гайды, runbook, troubleshooting.
- [ ] SOC 2 readiness: политики безопасности, access reviews, retention.
- [ ] SLA-документ, support-тиры, ответ на RFP/RFI.
- [ ] On-prem / private-cloud вариант (Helm chart / air-gapped).

**Приёмка:** типовой RFP enterprise-клиента закрывается имеющимися артефактами.

---

## Приоритеты

1. **Фаза 0** — без неё всё остальное «не считается» (нет гейта качества).
2. **Фаза 1** — безопасность — то, что спрашивает первый же enterprise-клиент.
3. **Фаза 3** — деньги: нельзя продавать без биллинга.
4. Фаза 2 — глубина продукта после того, как базовые продажи возможны.
5. Фазы 4–5 — масштаб и GTM по мере роста.

## Порядок действий прямо сейчас

1. Создать репозиторий git и пушить текущий код.
2. Настроить GitHub Actions (Фаза 0) — это можно сделать в тот же день.
3. Дальше по фазам, каждая — отдельный PR с тестами.
